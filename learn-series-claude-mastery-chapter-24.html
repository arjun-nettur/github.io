Computer Use & File Operations

When Claude Stops Talking About the Task and Starts Doing It

⏱️ 12 min read ◆ 📊 Advanced ◆ 🎯 Files & Automation

  • 2. Code Execution
  • 3. Generating Real Deliverables

Up to this point in the series, most of what has been asked of Claude ended in text — an answer, a draft, an outline that then had to be implemented by hand. Computer use changes that relationship. Instead of describing what to do with a file, Claude can open it, edit it, run code against it, and hand back a finished result. That shift comes with a responsibility: the thing being reviewed is no longer just words, it is actions taken on real files.

Quick Answer

Computer use with Claude means handing over a real file and getting back a finished result: Claude reads and edits the file, runs code for tasks that need exact counts or consistent rules, and generates deliverables such as spreadsheets, documents, and presentations. Results depend on precise before/after instructions, and trust depends on verification — automated checks built into the request, plus a manual spot-check of the output.

This chapter covers how to work with uploaded files directly, when to use code execution instead of an eyeballed answer, how to get real deliverables in the right format, and how to verify the output before relying on it.

1 How Do You Work With Files Directly Using Claude?

The starting point for most computer-use tasks is a file that already exists — a spreadsheet that needs cleaning, a document that needs edits, a folder of images that need renaming. Instead of describing the file's contents, the file itself gets handed over.

Being Specific About the Transformation

The quality of file-based work depends heavily on how precisely the before and after are described, not just the general goal.

I've uploaded 'Q3_expenses.xlsx'. It has one sheet with expense entries from three regions mixed together in a single column. I need: 1. A separate sheet for each region 2. Totals at the bottom of each sheet 3. A summary sheet comparing region totals side by side 4. Keep the original formatting for currency columns
❌ Vague Request
"Clean this up."

Leaves Claude guessing what "clean" means for this specific file — the result is a guess.

✅ Precise Request
"Split by region, add totals, build a summary sheet, keep currency formatting."

A specific before/after produces a specific result on the first pass.

Editing in Place vs. Producing a New Version

Decide upfront whether Claude should edit the original structure or produce something new, and say so. Two similar-sounding requests produce very different outputs.

In place: Edit this document in place — keep the existing headings and formatting, and only change the sections I've marked with [EDIT] in the text. New version: Use this document as a reference, but produce a new version with a different structure that covers the same content.
💡

Name the distinction explicitly: Stating whether the original should be preserved or replaced avoids a wasted first pass.

2 When Should You Ask Claude to Use Code Instead of Answering Directly?

Some tasks are technically possible to do "by eye," but far more reliable done with actual code — anything involving counting, calculating, cross-referencing, or applying a rule consistently across many items.

Good Candidates for Code Execution

  • Verifying a count, total, or calculation against a hard limit, such as a character count
  • Applying the same transformation to every row in a dataset
  • Cross-referencing two lists for matches or discrepancies
  • Anything where "close enough" isn't good enough
Rather than estimating, write and run a script that counts the exact number of words in each section of this document and confirms the total matches what I specified.
Key Insight

Preferring a verified calculation over an eyeballed one is exactly what prevents the quiet errors that slip through when a task is done "by feel."

Iterating on Code Output

Code execution isn't a one-shot process. The first result is a draft, and failing rows can be separated out before the transformation is applied to the full file.

Run this script and show me the output. If any rows fail the validation, list them separately so I can review before we apply the transformation to the full file.

3 How Do You Get Claude to Produce Real Deliverables?

Computer use means Claude can produce an actual file that gets downloaded and used — not just a description of what that file should contain. This is where the biggest time savings usually show up.

Naming the format explicitly — "I need this as an Excel file, not just a table in the chat" — ensures the result is something usable rather than something that then has to be reformatted by hand.

Iterative Building for Longer Deliverables

For anything substantial, ask for a structure first, confirm it, then let Claude build it out section by section rather than generating the whole thing in one pass.

Before building the full report, give me an outline of the sections and roughly how long each will be. Once I confirm, build it out.
💡

Same principle as Chapter 22: Confirm scope before committing to the full build — the same discipline that applies to project planning applies to file generation.

4 How Do You Verify Claude's Output Before Trusting It?

The fact that Claude produced a finished file doesn't mean the file is correct. Verification is a habit worth building deliberately, especially for anything with hard constraints such as character limits, specific numbers, or required formatting.

Building Verification Into the Request Itself

After generating this file, run a check that confirms: every row has a value in the required columns, the totals match the sum of the line items, and no currency values are negative. Report any rows that fail these checks.

Spot-Checking Before You Ship

Even with automated verification, a quick manual spot-check on a sample of the output catches things a script wasn't told to look for — a tone that's off, a section that reads awkwardly, formatting that is technically correct but looks wrong.

Why This Matters

Automated checks and human judgment aren't substitutes for each other. They catch different kinds of problems — the script catches what it was told to look for, and the human catches what nobody thought to ask about.

5 What Are the Most Common Computer Use Mistakes?

The same five mistakes account for most disappointing results from file-based work.

✕

Describing a file's contents instead of uploading it. Let Claude work with the actual file rather than a secondhand description.

✕

Vague transformation requests. "Clean this up" produces a guess. A specific before/after produces a result.

✕

Eyeballing something code could verify exactly. If there's a hard limit or count involved, ask for a script, not an estimate.

✕

Generating a long deliverable in one pass with no outline check. Confirm structure first, especially for anything substantial.

✕

Trusting a finished file without checking it. A file that looks complete isn't the same as a file that's correct.

◆ ◆ ◆
Key Takeaways
  • Upload the actual file — a real file beats a secondhand description every time
  • Describe the before and after precisely — "clean this up" is a guess, a specific transformation is a result
  • Say whether to edit in place or produce a new version — the two requests sound alike but produce very different outputs
  • Use code when "close enough" isn't good enough — counts, totals, and consistent rules belong to scripts, not estimates
  • Name the output format explicitly — Excel, document, presentation, or code file, not just a table in the chat
  • Outline first for long deliverables — confirm structure before the full build
  • Verify twice — automated checks inside the request, then a manual spot-check on a sample
Practice Exercises

Foundation Option

Upload a file already on hand — a spreadsheet, document, or list — and practice writing a precise before/after transformation request rather than a vague "improve this" prompt.

Advanced Option

Take a task normally done manually that involves some counting, calculating, or cross-referencing, and ask Claude to solve it with code instead. Compare the confidence in the code-verified answer versus a manually eyeballed one.

Reflection Questions

Where did being specific about the "after" state change the result? What is a task currently done manually that a script could verify more reliably? What would a useful verification step look like for the last file Claude was asked to produce?
